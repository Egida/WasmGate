# 01. Проблема и user-flow

> Документ для **введения ВКР**. Здесь формулируется проблема, целевая аудитория,
> сценарии «как сейчас» и «как должно быть», гипотезы и метрики успеха.

---

## 1. Контекст

Современный бэкенд — это десятки и сотни сервисов за одним входом. На границе
стоит прокси или API-шлюз, который терминирует соединения, маршрутизирует
трафик, применяет политики безопасности, лимиты и наблюдаемость.

Классические решения (nginx, Envoy, HAProxy, Kong, OpenResty) **умеют почти всё**,
но платят за это:

- сложностью конфигурации (DSL, xDS, Lua, C-модули);
- ресурсоёмкостью (память, вес образа, время старта);
- **дорогим расширением** — своя логика требует сборки нативного модуля,
  перезапуска или интерпретируемого Lua с паузами GC;
- **простоем при смене логики** (reload — это компромисс между «без обрыва» и
  «без утечек/дублей воркеров»).

Разработчику, которому нужно **одно кастомное правило** (например, лимит по
бизнес-ключу или тонкая защита от брутфорса), приходится либо изучать DSL, либо
писать C/Lua, либо ставить костыль в виде отдельного сервиса.

---

## 2. Постановка проблемы

> **Проблема:** современные прокси-шлюзы мощны, но **тяжеловесны в настройке и
> расширении**. Добавление или изменение кастомной логики требует глубоких знаний
> конкретного стека (C, Lua, xDS, DSL) и/или ведёт к **простою** сервиса при
> применении изменений (добавлении микросервиса и тп). Это замедляет TTM и повышает риск инцидентов на продакшн
> инцидентов на проде.

WasmGate формулирует контртезис: **расширяемость не обязана стоить
производительности**. Логику можно писать на любом языке, компилировать в WASM,
подхватывать **без рестарта**, и всё это — в прокси, который остаётся быстрым.

## 3. Почему существующие решения не закрывают боль

| Решение | Плюсы | Ограничения для нашей проблемы |
|---------|-------|--------------------------------|
| **nginx** | Эталон производительности, стабильность | Расширение = C-модуль (сборка, пересборка бинаря) или Lua (GC-паузы, exec); `reload` — graceful, но не «мгновенно и без нюансов» (старые воркеры, дублирование состояния); крутой DSL |
| **Envoy** | Мощная L7-модель, xDS | C++, тяжёлый, сложный, высокий порог входа, избыточен для средних задач |
| **HAProxy** | Топовый перф, надёжность | Lua ограничен по возможностям/перфу, конфиг сложный, расширение «вглубь» тяжело |
| **Kong / OpenResty** | Экосистема плагинов | LuaJIT + GC → непредсказуемая латентность; плагины на Lua; «своё» — снова Lua |
| **Traefik** | Go, простые конфиги, плагины | Плагины исполняются через интерпретатор (Yaegi) — медленнее нативной логики; ограниченный perf-бюджет |
| **Caddy** | Простые конфиги, Go | Плагины только на Go, требуют **пересборки** бинаря — не «легким движением» |

**Вывод:** на рынке есть либо «быстро, но не расширяемо/не гибко» (nginx,
HAProxy), либо «расширяемо, но медленно/тяжело» (Lua-стек, интерпретаторы,
нативные коллекции плагинов). **Ниша «быстро + расширяемо на любом языке +
без простоя» не закрыта.**

## 4. Целевая аудитория

| Персонаж                  | Роль                | Ключевая проблема                                          |
| ------------------------- | ------------------- | ---------------------------------------------------------- |
| **Платформенный инженер** | Владелец edge/шлюза | Нужно добавить политику/плагин, но это дорого и рискованно |
| **Backend-разработчик**   | Автор сервиса       | Хочет кастомную логику на границе, но не знает C/Lua       |
| **SRE / DevOps**          | Эксплуатация        | Боится `reload` и деградаций; хочет наблюдаемость          |
| **Security-инженер**      | Защита периметра    | Нужны собственные правила фильтрации без ломки прокси      |

## 5. Сценарии (Jobs To Be Done)

- **JTBD-1.** «Когда сервис атакуют боты, я хочу быстро добавить кастомное
  правило фильтрации, **не пересобирая и не перезапуская** прокси».
- **JTBD-2.** «Когда бизнес-логика маршрутизации меняется, я хочу применить
  новую конфигурацию **без единого разорванного соединения**».
- **JTBD-3.** «Когда мне нужна умная защита от DDoS, я хочу, чтобы она работала
  **в самом шлюзе**, а не отдельным сервисом».
- **JTBD-4.** «Когда мне нужна своя логика, я хочу писать её **на знакомом языке**
  (C#, Go, Rust, JS), а не учить чужой DSL».

## 6. User-flow

### 6.1. AS-IS — «как сейчас» (боль)

**Сценарий:** добавить кастомную защиту от брутфорса на `POST /login`.

```
1. Инженер читает мануалы по nginx/Lua/модулю.
2. Пишет либо C-модуль (сборка, ABI, пересборка бинаря nginx),
   либо Lua-скрипт (риск GC-пауз, ограниченный API).
3. Тестирует локально, собирает, готовит релиз.
4. Применяет: nginx -s reload.
   └─ Осторожно: старые воркеры живут, состояние дублируется,
      соединения могут «висеть», при ошибке — ручной откат.
5. Наблюдает метрики, ловит регресс по латентности.
```

**Боли на каждом шаге:** высокий порог входа · медленный цикл обратной связи ·
риск простоя/деградации · сложный откат · непредсказуемый перф (Lua/GC).

### 6.2. TO-BE — «как должно быть» (WasmGate)

```
1. Инженер пишет плагин на ЛЮБОМ языке (C#/Rust/Go/JS) против SDK.
2. Собирает в .wasm   →   wasm plugin build login-guard.wasm
3. Отправляет в Control Plane (C#):
      wasmgate plugin deploy login-guard.wasm \
         --hook on_data --target "route:/login"
   └─ Control Plane валидирует, версионирует, публикует.
4. Data Plane атомарно подхватывает новую версию:
      • новые соединения → новая логика;
      • старые соединения → доживают на прежней версии (drain).
   └─ НОЛЬ разорванных соединений, НОЛЬ рестарта.
5. Наблюдает метрики, при проблеме — мгновенный rollback на N-1.
```

**Выигрыш:** любой язык · секунды вместо часов · нет простоя · безопасный
sandbox · предсказуемая латентность (no GC-пауз в hot path) · простой откат.

### 6.3. Целевой пользовательский путь (сквозной)

```
Идея логики → плагин на знакомом языке → .wasm → deploy в Control Plane
   → hot-load в Data Plane → наблюдаемость → (нужно) rollback без простоя
```

## 7. Гипотезы

| ID     | Гипотеза                                                      | Критерий проверки                                                     |
| ------ | ------------------------------------------------------------- | --------------------------------------------------------------------- |
| **H1** | WASM-плагины дают **приемлемый оверхед** на fast path         | ≤ 5–10 % к латентности p99 при пустом/простом плагине vs. без плагина |
| **H2** | Hot reload возможен **без разрыва соединений**                | 0 dropped-соединений при N сменах конфига под нагрузкой               |
| **H3** | Rate limiting соединений на скользящем окне работает **в fast path без просадки** | throughput не падает > 5 % при включённом фильтре                     |
| **H4** | Прокси-ядро **конкурентоспособно** L4-аналогам                | throughput/latency в пределах ±10 % от nginx `stream` / HAProxy       |
| **H5** | «Любой язык → WASM» **снижает time-to-change**                | гипотетическое время добавления правила: часы → минуты                |

## 8. Метрики успеха

| Метрика | Baseline (ориентир) | Цель WasmGate | Как измеряем |
|---------|---------------------|---------------|--------------|
| Throughput (Gbps, L4) | nginx stream | ≥ 90 % от nginx | `iperf3`, `wrk2` |
| Латентность p99 (мкс) | прямые соединения | +≤ 100–200 мкс | `wrk2` / `vegeta` |
| Allocs/req на fast path | — | **0** (steady state) | `go test -benchmem` |
| Простой при reload | есть нюансы | **0 разорванных** соединений | chaos-тест reload под нагрузкой |
| Оверхед плагина | — | ≤ 5–10 % p99 | A/B с пустым плагином |
| Время применения конфига | секунды | < 100 мс (локально) | лог Control Plane |
| Память (RSS) | nginx | сопоставима или меньше | `ps`/pprof под нагрузкой |

## 9. Границы (что НЕ решаем)

- Не делаем «убийцу nginx» по всем фичам: не таргетим **полную** совместимость.
- Не строим GUI/маркетплейс плагинов на этапе ВКР.
- Не реализуем L7/HTTP-парсинг в первой волне MVP (L4 baseline → далее L7).
- Не претендуем на замену service mesh control plane (xDS) — только базовое
  управление.
- Не решаем сетевую безопасность уровня ОС (это зона eBPF и future work).

---

## 10. Ценность (для защиты)

1. **Практическая:** снижает time-to-change на периметре, убирает простой при
   смене логики, даёт встроенную защиту.
2. **Научно-техническая:** демонстрирует, что **WASM-песочница совместима с
   high-performance data plane** в Go, и как сохранить **zero-alloc** на fast path.
3. **Дифференциация:** новизна не в отдельных фичах (WASM-расширяемость, hot
   reload, rate limiting и Go-перф по частям есть у аналогов — ср. Envoy с
   `proxy-wasm` и xDS), а в их **сборке в одном компактном L4-ядре** с отдельным
   control plane и измеримым оверхедом.
